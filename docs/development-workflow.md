# “개발 진행해” 요청의 실행 절차

최종 갱신: **2026-10-15 (Asia/Seoul)**

사용자는 주제나 상세 요구사항을 반복해서 지정하지 않아도 된다. 개발자는 [로드맵](learning-roadmap.md)의 실행 대기열과 이 절차를 사용해 **선택 → 구현 → 독립 확인 → 수정 → 재검증 → 기록**을 마친다. 한 요청의 기본 단위는 인수 기준을 충족하는 작업 하나다. 이 절차를 추가한 것 자체가 챕터 구현·물리 검증 완료를 뜻하지 않는다.

실행 대기열은 로드맵 한 곳에서 관리한다. 물리 판정의 기준은 물리 검증 계획이며 로드맵은 그 근거를 연결한다. 시험 개수, 다음 작업, 통과 상태를 여러 문서에 복사하여 별도로 유지하지 않는다. 기록의 과거 시험 결과를 현재 결과로 해석하지 않는다.

## 시작과 작업 선택

1. 사용자 최신 지시와 위 문서를 읽는다. `git status --short --branch`, `git diff --stat`, 필요한 diff와 최근 로그로 기존 변경·현재 버전을 확인한다. 미완료 기록과 관련 검증 자료를 읽어 이미 한 작업을 반복하지 않는다.
2. **진행 중 작업의 남은 구현·검증을 먼저 재개**한다. 현재 작업이나 선행 챕터에서 핵심 설명 오류·계산 오류·동작 실패가 확인되면 이를 우선 수정한다. 별개 작업이면 대기열에 원인·재현 조건을 가진 복구 항목을 추가한다.
3. 진행 중 작업이 없으면 선행 조건을 충족한 가장 앞의 미착수 항목, 또는 차단 조건이 해소된 항목을 고른다. 뒤 항목을 먼저 고를 때는 선행 미충족·외부 차단 등 구체적 이유를 기록한다. 주제 선택만을 위해 사용자에게 되묻지 않는다.
4. 실행할 범위, 결과물, 제외 범위, 독립 검산과 사전 허용 오차, 관찰 과제, 인수 기준을 확정한다. 로드맵의 카드와 [챕터 설계 메모](chapter-authoring.md)를 사용하며 계산·근거의 세부 사항은 해당 검증 기록에 적는다.
5. 관련 시험과 전체 회귀 시험을 실행해 시작 상태를 확인한다. 알려진 기준 실패는 로드맵의 복구 항목과 대조한다. 이전부터 있던 실패와 이번 변경으로 생긴 실패를 구별하고 기존 실패를 정상으로 간주하지 않는다.
6. 바로 구현·수정에 착수한다. 설계 결정이 이미 문서로 정해져 있으면 계획 문서를 다시 만드는 것으로 개발을 대신하지 않는다.

우선순위는 **진행 중 작업의 결함·미검증 → 확인된 핵심 결함/실행 기반 복구 → 선행이 준비된 대기열 순서 → 후속 항목 구체화**이다. 기존 챕터 전체의 모든 교육 형식 보강을 마칠 때까지 새 챕터를 무기한 미루지 않는다. 새 챕터가 사용하는 핵심 개념·모형의 검증은 먼저 마친다.

## 구현과 검증

- 기존 정적 HTML·로컬 자산 구조를 유지하고, 같은 현상의 순수 계산은 기존 공통 자산을 우선 재사용한다. 불필요한 프레임워크·빌드 과정·외부 CDN을 추가하지 않는다.
- 공통 모델의 좌표·부호·단위와 기존 호출자를 확인한다. 페이지마다 시간축·detuning·정규화를 임의로 바꾸지 않으며 다른 규약은 변환과 정의를 명시한다. 공통 모델 변경은 모든 사용 챕터를 영향 범위에 넣는다.
- 새 계산은 독립 해석·적분·불변량 등으로 검산한다. 난수 실험은 seed·표본 수·통계 기준을 기록하여 재현 가능하게 한다. 기존 시험이 충분한 문구 수정에 구현을 복제한 시험을 늘리지 않는다.
- 실제 브라우저에서 대표 상태·관찰 과제·경계·초기화·키보드 조작을 확인한다. 데스크톱은 가능하면 1920px, 모바일은 390px 전후를 사용한다. 화면 전체의 가로 넘침·빈 canvas·겹침과 조작 후 표·그림·정답의 일치를 확인한다.
- 설명·수식·단위·근사·도식·퀴즈의 정합성을 [물리 검증 계획](physics-validation-plan.md)에 따라 판정한다. **시험 통과, 실제 화면 확인, 물리 판정, 외부 전문가 검토는 서로 대체할 수 없다.**
- 발견한 문제를 수정한 뒤 해당 재현 조건과 영향받는 기존 동작을 재검증한다. 최종 코드 변경 뒤 관련 시험과 전체 회귀 시험을 실행한다. 결과가 유효한 동안 이유 없이 같은 검증을 반복하지 않는다.

### 실행 환경과 기록

저장소 루트에서 실행한다. 먼저 `node --version`으로 사용 버전을 확인한다. 프로젝트 시험은 Node 내장 기능을 사용한다.

```powershell
node --test tests/*.test.cjs
```

`file:`로 동작하는 정적 페이지도 확인할 수 있다. 로컬 HTTP가 필요하면 별도 터미널에서 다음을 실행하고 `http://127.0.0.1:8765/docs/<페이지>.html`을 연다. 포트 충돌 시 다른 포트와 실제 URL을 기록한다. 실행 가능한 브라우저 도구·CLI를 사용하며 새 의존성이 필요하면 필요성과 설치 범위를 확인한다.

```powershell
python -m http.server 8765 --bind 127.0.0.1
```

화면 기록에는 URL·브라우저·viewport·조작·관찰 결과를 적고 대표 스크린샷을 저장하여 직접 확인한다. 시험 stdout이나 DOM/canvas stub 결과를 스크린샷 검증으로 기록하지 않는다. 보고서 생성기는 실제 입력 파일·날짜·출력 경로를 확인한 뒤 실행하고, 기존 날짜에 고정된 스크립트가 과거 기록을 덮어쓰지 않게 한다.

## 작업 완료 기준

챕터의 구현·보강 작업은 다음을 충족해야 대기열에서 **완료**로 바꾼다.

1. 카드에 지정한 학습 목표·관찰 과제·확인 문제·조작이 실제 페이지에 있고, 제외 범위가 지켜진다.
2. 독립 확인과 관련 시험·전체 회귀 시험이 통과한다. 사전 실패가 남으면 별도 복구 기록과 영향 범위를 연결하며 **전체 시험 통과라고 쓰지 않는다**. 관련 실패나 미해결 핵심 결함이 있는 작업은 완료할 수 없다.
3. 실제 데스크톱·모바일 화면과 대표 조작을 확인하고 근거를 저장한다.
4. 해당 변경 범위의 물리 판정이 **대상 버전 통과**이고, 검증 기록에 대상 파일 버전·근거·한계가 있다. 이전 변경까지 포괄한 전면 통과로 확대하지 않는다.
5. 로드맵·물리 검증 계획을 갱신하고, 새 페이지는 포털·README 및 실제 선행/후속 페이지에 연결한다. 없는 페이지에는 링크를 만들지 않는다.
6. 다음 실행 항목과 인수 기준이 남아 있다. 완료한 작업의 결과 기록을 연결하고 최종 diff에서 범위 이탈·기존 사용자 변경 손상을 확인한다.

문서만 수정하거나 도구·시험을 복구하는 작업은 해당 카드의 인수 기준을 적용한다. 화면을 바꾸지 않은 문서 작업에 챕터 화면 검증을 요구하지 않는다. **외부 전문가 검토는 별도 상태**로 유지하며 교육용 구현의 완료 조건으로 일괄 강제하지 않는다. 실제 임상 영상은 출처·사용 조건을 확보할 때 보강하고, 기본 개발은 교육용임을 표시한 합성 모형으로 진행한다.

## 중단·차단·재개

- 작업 상태는 **미착수 / 진행 중 / 차단 / 완료**로 기록한다. 선행 조건이 남은 미착수와 외부 요인에 막힌 차단을 구별한다. 한 시점의 진행 중 작업은 하나로 유지한다.
- 한 요청에서 끝내기 어려우면 검증 가능한 작은 하위 항목으로 나누되 부모 챕터의 남은 범위를 보존한다. 검증이 빠진 부분 구현을 완료로 올리지 않는다.
- 환경·접근·근거 문제는 원인 확인과 가능한 대체 방법을 시도한다. 실제 브라우저를 쓸 수 없으면 가능한 계산·내용 검토를 진행하되 화면 확인은 미수행으로 남긴다. 미검증 챕터를 계속 쌓지 않고 독립적인 문서·복구 작업을 선택한다.
- 사용자 입력이 정말 필요한 차단이면 이유와 필요한 입력을 짧게 알린다. 답 없이 결정할 수 있는 파일명·배치·예시값 선택까지 차단으로 취급하지 않는다. 동일 차단이 해소되지 않은 다음 요청에서는 기록을 확인하고 반복 시도 대신 가능한 독립 작업을 진행한다.
- 사용자 파일을 덮어쓰거나 reset·자동 stash로 시작 상태를 바꾸지 않는다. 출처를 모르는 미완료 변경은 먼저 diff를 확인한다. 별도 개발 세션이 같은 파일을 작업 중이면 충돌하지 않는 범위를 선택한다.

미완료/차단 시 로드맵의 해당 작업에 아래 메모를 남긴다. 일반 결과와 증거는 링크하고 중복해서 복사하지 않는다.

```text
작업 ID / 상태 / 날짜:
변경한 파일 / 이미 끝낸 범위:
수행한 검증과 결과 링크 / 아직 수행하지 않은 검증:
남은 결함·차단 원인 / 시도한 대체 방법 / 재개 조건:
다음 요청에서 실행할 첫 행동 (파일·함수·명령 또는 재현 조건):
```

## 대기열을 소진한 뒤

로드맵의 후속 단계에서 선행 조건을 충족한 첫 주제를 선택해 카드로 승격하고 구현한다. 착수 전 최소한 **중심 질문, 최대 세 목표, 2–3개 관찰 과제, 조작·기본값·허용 범위, 계산·표시 가정, 독립 확인, 제외 범위, 인수 기준**을 구체화한다. 새로운 과학적 내용의 근거는 실제 자료로 확인하며 제품·안전·임상 수치의 최신성도 확인한다.

대기열에는 현재 작업 이후의 다음 세 작업 이상을 선행 조건과 함께 유지한다. 기존 작업 ID를 재번호·재사용하지 않고 새 항목에는 다음 번호를 부여한다. 확장 후보는 하나의 큰 페이지로 자동 구현하지 않고 기존 챕터 ID를 추적할 수 있게 소주제로 나눈다. 외부 차단이 없는데도 “다음 할 일을 지정해 달라”는 이유로 개발을 끝내지 않는다.

최종 보고에는 **처리한 작업 ID와 바뀐 학습 경험, 수행한 검증과 제한, 다음 작업**을 간결하게 적는다. 커밋·푸시·게시 여부는 실제 수행 사실대로 구분한다.
